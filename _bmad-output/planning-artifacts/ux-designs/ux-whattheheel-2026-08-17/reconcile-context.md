# Reconciliation: UX Spine (DESIGN.md / EXPERIENCE.md) vs. project-context.md

**Scope:** Spine-vs-standing-conventions consistency only (TS strict, PascalCase, Server/Client Component split, `useState`-only local state, no `alert()`, no direct DOM manipulation, Tailwind CSS v4 styling). PRD/architecture/epics fidelity and visual quality are out of scope for this check.

**Verdict:** The spine pair is consistent with project-context.md. No forbidden patterns (native `alert()`, imperative DOM manipulation, non-PascalCase component naming, non-Tailwind styling system) are present or implied. Three low-severity items are worth a note for implementers but are not conflicts.

## Checks passed

- **No `alert()` / native browser notification anywhere.** Every error state (VTO failure, upload validation, registration/login failure) is specified as an inline, in-page component (`{components.inline-error}`), explicitly "never a modal" (AD-6). Success feedback ("Selfie saved.") is also specified as in-page plain-register text, not a native dialog. Fully compliant with project-context's "avoid native `alert()`, implement integrated UI feedback" rule.
- **No direct DOM manipulation implied.** Drag/scale/rotate on `OverlayCanvas.tsx` is described as pointer-events-driven with state-backed slider/button controls and a keyboard-equivalent (arrow keys/`+`/`-`/`[`/`]`) — a declarative, state-driven interaction model consistent with "prefer React's declarative approach." Nothing in the spine calls for `document.querySelector`, manual class toggling, or other imperative DOM code.
- **PascalCase naming.** The one literal component filename named in the spine, `OverlayCanvas.tsx` (EXPERIENCE.md, Component Patterns and Accessibility Floor), is correctly PascalCase. All other component references (`trend-card`, `badge`, `nav-tab-bar`, etc.) are kebab-case DESIGN.md *token* keys, not file/component names, so they don't conflict with the PascalCase component-naming rule.
- **Tailwind v4 compatible styling model.** EXPERIENCE.md's Foundation section explicitly states: "No UI system is named — this is Tailwind CSS v4 utility classes only, no shadcn/MUI/internal component library underneath." DESIGN.md's tokens (colors, spacing scale, radius, shadow strings) are expressed as a design-token set referenced via `{colors.x}` / `{spacing.x}` paths, which maps cleanly onto a Tailwind v4 `@theme` config or arbitrary-value utility classes — nothing assumes CSS-in-JS (styled-components/emotion) or SCSS variables/mixins.
- **Client/Server Component split not violated.** Only genuinely interactive surfaces (`OverlayCanvas.tsx`, VTO polling, forms) are implied to need `'use client'`; static content (Feed grid render, trend card display) is not forced into client-only patterns by anything in the spine.
- **No global state library implied.** Nothing in the spine calls for Redux/Zustand/Context-as-global-store; state described (canvas transform values, form fields, polling status) reads as component-local.

## Minor notes (not violations, worth flagging for implementers)

1. **"Canvas" naming ambiguity in `OverlayCanvas.tsx`.** EXPERIENCE.md's Component Patterns row says "Foot photo and shoe image are both `<img>`/canvas layers held only in component state" and DESIGN.md calls the component `overlay-canvas`. This term could be read as literally requiring an HTML5 `<canvas>` element with imperative `getContext('2d')`/`drawImage` calls, which would push toward the direct-DOM-manipulation pattern project-context asks to minimize. The spine's own language ("`<img>`/canvas layers," CSS-token-driven background/border) is more consistent with a `div`-based stage holding absolutely-positioned `<img>` elements moved via CSS `transform` bound to React state — fully declarative. Recommend the dev/architecture handoff clarify that "canvas" here is the component's visual stage, not the HTML5 Canvas API, so implementers don't default to the imperative-drawing approach.
2. **Typography tokens read as a design-token schema, not literal Tailwind classes.** DESIGN.md's `typography.*` entries (`fontFamily`, `fontSize`, `fontWeight`, `lineHeight`, `letterSpacing` as camelCase fields with raw px/em values) are a portable design-token format, not literal Tailwind utility class names or Tailwind's default type scale. This is normal for a design spec and not a CSS-in-JS assumption, but it does mean a translation step (Tailwind v4 `@theme` custom tokens, or arbitrary-value utilities like `text-[13px]`) is needed at implementation time rather than the values mapping onto Tailwind's default scale out of the box.
3. **Cross-screen state ("carried-over selected trend") has no storage mechanism specified.** EXPERIENCE.md's Key Flows describe a trend selection persisting from Feed → Registration → AI Stylist across full page/route transitions (Flow 1 step 6, Flow 2 step 3). Plain `useState` does not survive a navigation/remount, so this will need a deliberate, scoped mechanism (e.g., URL/query param, server session, or `sessionStorage`) rather than component state — worth calling out so an implementer doesn't reach for a global state library (which project-context says to avoid "unless necessary") when a simpler scoped mechanism would do.

## Items not found (checked for, absent — good)

- No CSS-in-JS or SCSS assumptions in either file.
- No non-PascalCase component file names.
- No modal-based error/notification pattern.
- No light-mode/theme-toggle code path (explicitly forbidden in EXPERIENCE.md's own "Banned" list, which aligns with, not contradicts, project-context).
