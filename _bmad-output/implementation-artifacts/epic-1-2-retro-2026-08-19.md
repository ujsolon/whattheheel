## What went well

**The layered architecture held for eleven stories.** Every external call stayed in `lib/external/*`, every MongoDB access in `lib/data/*`, orchestration in `lib/services/*`. No story leaked across those boundaries. This is what made reviews sharp — when a finding said "this belongs in the service layer," there was an unambiguous answer about where that was.

**The locked-copy contract survived implementation.** Six error strings specified verbatim in `EXPERIENCE.md`, verified codepoint-by-codepoint during the Story 2.4 audit — em dashes, curly apostrophes, trailing periods all exact. Content contracts usually erode on contact with code; this one didn't.

**Live verification caught what mocks could not.** Story 2.3 found that YouCam returns `task_status`, not `status` — meaning a genuinely successful generation would have been invisible to the app permanently. The same session found a 300-second signed URL expiring before YouCam's queue reached it. Neither is reachable by any amount of mocked testing.

**Security boundaries were correct and tested.** No secret was ever `NEXT_PUBLIC_`-prefixed. The 404-not-403 ownership rule for foreign task ids has explicit regression coverage. Auth checks live in the service layer, not only at the HTTP edge.

**Deferrals were documented as deferrals.** Every conscious trade-off was written down with its reasoning. This is the sole reason `production-readiness.md` could be assembled from the record rather than rediscovered in production.

## What didn't

### 1. Concurrent sessions on a shared tree caused repeated, documented friction

- Story 2.1 found uncommitted breakage from an in-flight Story 1.3 attempt and had to scope its verification gates around it.
- Story 1.3 recorded a transient full-suite failure caused by Story 2.1's test files landing mid-run.
- An `OverlayCanvas` copy change floated unattributed in the working tree across **two** separate code reviews before being traced to a commit.
- During Story 2.5's review, a concurrent session committed the work between two commands, changing the diff mid-analysis.

**Root cause:** parallel work on one tree with no branch isolation. Adopted under deadline pressure; the coordination cost exceeded the parallelism gain.

### 2. Deferred decisions became the next story's defects

Story 2.3 deferred the error map to 2.4. Story 2.6 deferred durability until forced. Story 2.5 scoped Buy Now to the VTO result — reversed within a day by CR-03 and Story 2.8.

Each deferral was individually reasoned. Collectively they pushed defects into the **seams between stories**, where no single story's review was looking. The sharpest instance: the Cloudinary copy-failure code added during the 2.6 review flowed into 2.4's error map and told users their *preview* had failed and to replace an innocent selfie — when generation had actually succeeded and been billed for.

### 3. The same bug class appeared twice, independently

A value resolved correctly on the fresh-poll path but forgotten on the reload path: Story 2.4 hit it with `errorCode`, Story 2.6 hit it with `resultUrl`. Found separately, by separate reviews. **A retrospective after Story 2.4 would have named the class before 2.6 walked into it.** This is the concrete cost of deferring retros.

### 4. Specs and code drifted; only review caught it

Story 2.4's AC4 described behaviour the implementation deliberately improved on, and nobody updated the AC. Story 2.5's AC4 excluded history until 2.8 reversed it. `EXPERIENCE.md` said trend cards had "no secondary action" right up until they did.

All were reconciled — but only because a review went looking. That is detection, not prevention.

### 5. Test count overstated coverage

320 passing tests invites confidence the assertions don't earn. Reviews repeatedly found tests that could not fail:

- a style assertion re-typing the component's own class strings — passes even if those classes resolve to nothing
- a test named *"transitions to the generic error message"* asserting only that an alert **existed**, never its text
- a pinch-gesture test asserting `toBeGreaterThan(1)` — passes at 1.0001
- Story 2.5's seed guard was entirely dead code while every `buyUrl` was `null`, so its "real-seed conformance" claim covered nothing
- two tests mocking a response shape the server could no longer produce

### 6. Two stories had no verifiable baseline

Stories 1.1 and 2.5 carried `baseline_commit: NO_VCS` in a repository with clean git history. Story 2.5's review baseline had to be derived from the commit graph. A wrong baseline silently reviews the wrong code.

### 7. Nobody owned the risks nobody thought to incur

The process tracked consciously-incurred debt well and was blind to everything else. Epic 2 shipped storing **face images** — indefinitely, transmitted to a third-party processor — with no privacy policy, no consent step, no deletion path, and no `deleteVtoResult` to delete them with. `POST /api/vto-tasks` spends 2 metered units behind nothing but an auth gate, fronted by free unverified registration.

Neither is a bug, and both were correct hackathon trades. What's notable is that **no story ever owned them** — they were never anyone's acceptance criteria, and surfaced only when `production-readiness.md` was written at MVP close.
